# SciReader EN–RU — предварительная архитектура

Дата: 2026-11-05. Стек принят; состав модулей и алгоритмы ниже являются предложением для проверки. Создан ограниченный прототип; проверенные возможности и ограничения описаны в [отчёте](prototype.md). [ТЗ](requirements.md) определяет поведение, [решения](decisions.md) — основания и открытые вопросы.

## 1. Выбранная платформа

Статическое приложение React + TypeScript, сборка Vite, PDF.js для оригинала и извлечения текста, MathJax для LaTeX вне изображения PDF, PWA, Playwright для браузерных сценариев. Хостинг — GitHub Pages. Версии зависимостей прототипа зафиксированы в package.json и package-lock.json. Постоянное хранение и PWA ещё не реализованы.

Сервер не обязателен. Подготовка запросов и импорт ответов внешнего чата выполняются локально. Никаких автоматических обращений к ИИ только из-за загрузки PDF.

## 2. Предлагаемые границы модулей

| Модуль | Ответственность |
| --- | --- |
| Источник PDF | Оригинальные байты, идентичность документа, страницы, исходные текстовые элементы |
| Извлечение и привязки | Порядок чтения, нормализация переносов, связи текста с областями страницы, статус проверки |
| Модель чтения | Предложения, математические фрагменты, отрывки, контрольные точки, подсчёт |
| Перевод | Подготовка запроса, проверка ответа, сравнение версий и применение выбранных изменений |
| Ридер | PDF, русский текст, выбор, подсветка, масштаб и навигация |
| Формулы и произношение | LaTeX, английское чтение, подсказки, синтез речи, переход к словарю |
| Хранение | Папка/IndexedDB через общий контракт, переносимый пакет, ошибки и резервные копии |

Не вводить отдельные сервисы или сложную систему плагинов ради этих границ. Достаточно явных модулей внутри одного приложения.

## 3. Поток данных

```text
PDF → исходные текстовые элементы и координаты
    → нормализованные фрагменты + карта соответствия источнику
    → выбор старта и N → отрывок
    → запрос внешнему ИИ → проверка ответа → перевод
    → ридер: оригинальный PDF + связанные русские фрагменты
```

Оригинал, нормализованный текст и перевод — разные сущности. Нормализация не пересохраняет PDF. Геометрию формирует приложение; ответ ИИ не может заменить её без явной процедуры проверки.

## 4. PDF и подсветка: гипотеза реализации

- PDF.js отображает страницу; текстовый слой используется для взаимодействия и сопоставления с извлечёнными элементами.
- Предложение ссылается на несколько областей, возможно на разных страницах. Подсветка рисуется отдельным полупрозрачным слоем без изменения размеров букв.
- Координаты хранятся в устойчивой системе страницы, а не в пикселях текущего окна. Масштаб, поворот и смещение применяются при отображении.
- Для части текстового элемента нужна привязка к диапазону символов; ширина всего элемента недостаточна для предложения, начинающегося посреди строки.
- Геометрию формул можно исправлять вручную. Автоматическое распознавание LaTeX не входит в возможности обычного извлечения PDF.js само по себе.
- Статусы «автоматически извлечено», «требует проверки», «проверено» не смешиваются.

Эксперимент должен определить точную работу с лигатурами, дефисами, несколькими колонками, текстовыми элементами и границами формул. Нельзя заранее утверждать, что любой PDF с текстовым слоем обработается без исправлений.

## 5. Перевод без привязки к одному сервису

Перевод хранится на уровне статьи и используется всеми её отрывками. При изменении одного фрагмента обновляются все представления, без копирования текста в каждый отрывок.

Для ридера согласованы два режима прокрутки и соединительная фигура между соответствующими фрагментами. Предлагаемая реализация: общая карта привязок управляет подсветкой, соединителями и синхронизацией; якорь связанной прокрутки выбирается по видимому фрагменту. Нужны защита от обратной передачи события второй панели и явное поведение вне переведённого диапазона. Точный алгоритм проверить прототипом; нельзя считать синхронизацией равные проценты высоты страниц.

Общий контракт запроса/ответа используется независимо от внешнего чата. Первый способ доставки — пользователь вручную переносит промпт и файл. Будущая API-интеграция должна возвращать тот же логический результат, а не вводить другую модель статьи.

Ответ проверяется до изменения сохранённых данных. Изменённые вручную фрагменты участвуют в сравнении, а не заменяются по принципу «последний ответ победил». Не исполнять полученный от модели HTML или скрипты. Терминологический контекст можно передавать в запросе; учебный глоссарий не создаётся.

## 6. Хранение

Принят подход [hotkey-map](https://github.com/dmitrii-a-piskunov/hotkey-map): отдельные реализации папки и IndexedDB за одним интерфейсом. На момент изучения исходников commit `896871a2d828302358ed5131e10be053e781caf2` содержит автосохранение, резервные копии, восстановление доступа и защиту от второй вкладки. Это ориентир, не обязательство копировать каждую деталь.

Предложение структуры пользовательской папки (не структура репозитория):

```text
library.json
articles/<article-id>/source.pdf
articles/<article-id>/document.json
backups/
```

PDF хранится отдельно от часто изменяемых данных. В IndexedDB ему соответствует бинарный объект. Для переносимого экспорта предлагается архив с PDF и JSON, но окончательное решение зависит от Q-02/Q-08.

Нужно спроектировать согласованную запись нескольких файлов, миграции версии и восстановление после сбоя. Атомарная запись одного JSON не означает атомарность всего пакета. Облачный клиент не обеспечивает автоматическое разрешение конфликтов приложения. Рекомендуется проверка внешних изменений перед записью и последовательная работа на одном устройстве; политика ещё открыта (Q-04).

## 7. Автономность и публикация

Сборка публикуется как статические ресурсы. Пользовательские документы хранятся отдельно и не попадают в сборку. `references/` не копируется в публичные ресурсы автоматически.

PWA кэширует оболочку и необходимые ресурсы для просмотра подготовленных материалов. Обновление приложения не должно требовать очистки пользовательского хранилища. Детали миграций и обновления service worker определить при программном каркасе.

Словарь открывается по явному действию. Встраивание стороннего сайта допустимо только после проверки его технических возможностей. Офлайн-работу внешнего словаря и сетевых голосов не обещаем.

## 8. Основные риски и способы проверки

| Риск | Проверка / ограничение |
| --- | --- |
| Ошибочная привязка предложения | Сверка на исходных страницах, разные масштабы, ручное исправление неоднозначности |
| Потеря математических обозначений | Встроенные и отдельные формулы проверяются по PDF, чтение редактируется отдельно |
| Сдвиг контрольных точек после правки | Версия текста, устойчивые ID, контекст позиции и явная перепривязка |
| Потеря ручного перевода при импорте | Предпросмотр различий и явное применение |
| Конфликты облачной папки | Обнаружение внешней версии, согласование Q-04; не полагаться на блокировку вкладки как межустройственную |
| Различия браузеров | Общая функциональность, разные адаптеры хранения, реальная матрица Q-06 |
